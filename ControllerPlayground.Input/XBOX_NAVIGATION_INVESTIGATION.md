# Increment 3 Xbox navigation regression investigation

## Hardware follow-up: Steam Input confirmed by the user

After reproducing the remaining tile skipping and B-triggered Game Details in
Visual Studio Debug, the user identified Steam Input Desktop Layout mappings
injecting keyboard/mouse input alongside GameInput as the cause. Disabling those
desktop mappings eliminated the problems. The user subsequently confirmed all
manual Increment 3 Xbox + DualSense tests passed; see OWNERSHIP.md for the final
verification record. This is a user-performed hardware result, not an automated
reproduction.

The shell logs showed managed Back followed by Game Details focus without an
intervening managed Accept. Steam Input keyboard/mouse emulation is consistent
with an additional activation outside the attributed route. The precise Steam
binding was not captured, so no particular keyboard key or mouse binding is
claimed as verified. The earlier WinUI filter gap remains a valid defensive
correction, but did not resolve the reported Steam Input interference.

Do not change native button mappings or repeat thresholds to compensate. Normal
keyboard/mouse events generated by Steam cannot safely be blocked by guessing
that they came from a controller. Steam configuration was not changed by the
agent; KeyboardHost IPC and GameInput policies are unchanged. Detailed tracing
remains opt-in. The user subsequently confirmed the held-input reconnect
neutral-gating check passed on October 25, 2026; this is user-performed hardware
verification rather than an automated or agent-observed result.

This review preserves the existing uncommitted Increment 3 work. No commits,
KeyboardHost IPC changes, native changes, or GameInput focus-policy changes were
made. The investigation below records the initial uncertainty; subsequent
user-performed hardware results are recorded above.

## Findings before changing behavior

### Confirmed duplicate UI path

MainWindow has one 16 ms timer and calls `ControllerService.PollActions()` once
per tick. There is no shell `PollAction()` call and no shell `ActionReceived`
subscriber dispatching the batch again. KeyboardHost calls `PollAction()` in its
own process, with the shell blocked during its handoff. The native legacy cursor
is not polled by MainWindow's attributed source.

The second shell path is WinUI keyboard/focus processing. The preview filter
checked only `args.Key` in the Gamepad numeric range 195–218. WinUI can present
A as Space and B as Escape, with the original Gamepad or Navigation identity in
`OriginalKey`. Navigation aliases 136–143 were also missing from the filter.
Home and Library explicitly enable XY keyboard focus navigation, while their
managed handlers also call `TryMoveFocus` or schedule grid focus changes.

Consequently, one controller input could reach both WinUI's automatic navigation
or button processing and the managed router. B mapped to Escape could close a
scope in the preview handler, then its attributed Back could affect the newly
exposed page. This bypass also ran outside the ownership check.

Small behavior correction: use the tested `ShellKeyPolicy` to suppress a routed
key when **either Key or OriginalKey** identifies a Gamepad or Navigation alias.
Apply it to both preview key-down and key-up, before physical Escape handling.
Actual physical Space/Escape/Enter/arrows/Tab/F1/F10 remain available. This is a
local XAML filter; no system-wide hook or gameplay suppression was added.

References: Microsoft's [KeyRoutedEventArgs mapping table](https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.ui.xaml.input.keyroutedeventargs)
and [VirtualKey values](https://learn.microsoft.com/en-us/uwp/api/windows.system.virtualkey).

### Native and managed normalization

- `ReadControllerState` copies GameInput gamepad buttons/axes without an Xbox
  remapping branch. Installed GameInput headers agree with the managed masks:
  A = `0x4`, B = `0x8`, D-pad = `0x40/0x80/0x100/0x200`.
- `PollHistory` uses independent per-device cursors/baselines, accumulates brief
  button edges, and retains the existing short-stick-flick projection separately
  from actual axes. `NativeControllerInputSource` polls snapshots, queries the
  matching ID/generation projection and drains native diagnostics. Input/Guide
  diagnostic events are not translated again as actions.
- `ControllerDeviceState` independently tracks buttons, stick direction, repeat
  deadlines and neutral gates. D-pad has precedence over stick; one direction
  emerges per poll. Repeat remains 400 ms initially, then 120 ms, without a
  catch-up loop. Stick press/release remain 0.65/0.30 with 0.15 axis-switch margin.
- Router authorization runs before MainWindow Guide/View dispatch. Scope changes
  block the rest of the precomputed batch and suppress held controls. These
  safeguards did not cover the unfiltered WinUI event path.
- Managed Back has an early-return path in MainWindow. It cannot fall into the
  page's Accept handler. Guide closes Back without forwarding it to the view.

No evidence from source or synthetic tests justifies changing native capture,
timing thresholds, hysteresis, or A/B mapping. Those behaviors were left intact.
Their behavior on the reported Xbox hardware still needs the trace below.

### B-triggered launch remains a distinct hardware question

Synthetic B-only input produces only Back, including held input and brief taps;
it never produces Accept. The Escape bypass explains double Back effects, but
does **not establish** why a B press reportedly launched a game. Do not mark that
symptom resolved without retesting. The new trace records actual game launches,
Guide clicks, tile clicks/activation, navigation commands and their current
action context. A B-only trace should contain Back/close/history navigation and
no Accept, Click activation or launch command. A genuine Back operation can
return to Library if that is the previous screen in navigation history.

Third-party input remapping that emits ordinary keyboard keys with an ordinary
OriginalKey cannot be identified as a controller by this filter. The trace makes
such events visible; physical keyboard recovery must not be disabled by guessing
their source.

## Temporary diagnostic logging

Enable only for the retest in the PowerShell process used to launch the Debug
shell (or the parent process used to start the debugger):

```powershell
$env:CONTROLLERPLAYGROUND_INPUT_TRACE = '1'
& .\bin\x64\Debug\net8.0-windows10.0.19041.0\ControllerPlayground.exe
```

Use your usual Debug deployment/launch if the app requires it, inheriting this
environment variable. Close any older shell instance first. This command assumes
the repository root. Close the application before disabling the setting:

```powershell
Remove-Item Env:\CONTROLLERPLAYGROUND_INPUT_TRACE
```

Files: `%LOCALAPPDATA%\ControllerPlayground\Logs\ownership-*.log`.
Detailed logs are intentionally verbose and may add diagnostic overhead; compare
navigation once with the variable removed after capturing a failure. They contain
no typed chat text or credentials. No extra native polling is performed.

- UTC and monotonic observation timestamps are written with every line.
- `NATIVE_EVENT`: native event sequence, ID/generation, native timestamp, raw
  buttons/pressed/released masks and left-stick axes. Events and snapshots are
  separate observations; correlate ID/generation/time, not a guessed one-to-one
  association. Held repeats may have no new native event sequence.
- `SAMPLE` / `TRANSLATE`: actual axes, projected axes, raw masks, reading/history
  availability, neutral gate, translated actions, repeat flags, previous buttons,
  stick hysteresis direction, held direction and next repeat deadline.
- `ACTION`: managed sequence, ID/generation, native/observed time, action, repeat,
  owner decision, scope and current focus. Discarded actions execute no command.
- `XAML_KEY`: mapped/original keys, XAML device string, repeat count, current
  focus and suppression result. XAML device strings are not claimed to be the
  native full device ID. No identity is fabricated for unattributed events.
- `FOCUS_REQUEST` / `FOCUS`: old/new focus names and actual focus changes.
- `DISPATCH` / `DISPATCH_DONE` and `COMMAND`: before/after focus and scope,
  navigation, Guide/tile/context activation and actual Steam launch calls.
  Synchronous commands carry their managed action sequence/device; pointer,
  physical keyboard or asynchronous commands are explicitly unattributed.

The diagnostic changes are in ControllerService, ControllerDeviceState,
NativeControllerInputSource, MainWindow.Input, OwnershipTrace, and the relevant
Guide/context/tile/navigation/game-launch command entry points. The behavior
correction is ShellKeyPolicy plus its two MainWindow preview-event call sites.

## Hardware retest: Xbox first, then DualSense

1. In Home and Library, do ten separate short D-pad taps in each usable
   direction, releasing fully between taps. Each action must move one selection,
   except at an edge. Hold for two seconds: expect an immediate move, a roughly
   400 ms pause, then roughly 120 ms repeats; releasing stops immediately.
2. Make short left-stick movements in each direction, return to center, then
   test a hold and small diagonal jitter. Expect one initial move, controlled
   repeats, no post-neutral move, and no extra XAML focus jump. Check both Home's
   horizontal list and Library's grid, including row/filter boundaries.
3. Test B alone on Home, Library, Game Details with Play focused, each context
   menu, and Guide with Library/Resume selected. B may close one scope or perform
   one history Back, but must never click, accept or launch. Test A separately:
   exactly one activation. Include fast A-release-then-B to expose late key-up
   activation and verify physical Space/Enter/Escape separately.
4. Open Guide using Xbox. Try DualSense directions, Cross, Circle, PS and touchpad
   View. They must not move, activate or close it. Repeat with DualSense as owner
   and Xbox as non-owner. Confirm mapped XAML A/B/Navigation events show
   `suppressed=True` and attributed non-owner actions show `Discarded`.
5. Open/close Guide while holding another direction or A/B. No input may fall
   through to the underlying view. Release before continuing. Include Guide+B
   together, nested Friends/Chat/Guide, disconnect takeover, and physical Escape
   recovery. Verify no stale activation occurs on the newly restored focus.
6. The explicit held-input reconnect test was subsequently **user-verified**:
   hold A/Cross or a direction through reconnect for each controller, verify no
   action until release/neutral, then explicitly claim and activate separately.
7. Close the app and repeat the simple navigation/B checks with detailed tracing
   disabled. Existing gameplay and background Guide behavior must remain intact.

If anything fails, retain the newest log and note the approximate time, controller,
button and screen. In particular, a B-only launch requires the lines from the
raw sample through the launch command before concluding its cause is fixed.

## Automated coverage

The dependency-free runner retains all 21 managed input and 19 ownership groups
and adds 8 navigation groups: mapped A/B, all gamepad/navigation aliases, physical
keyboard preservation, B-only press/hold/tap, short D-pad presses, repeat timing,
stick jitter/neutral, and non-owner Back/Accept/Guide rejection.

These tests validate policy and native-shaped managed input; they do not drive
real WinUI controls or prove hardware behavior. Native structures and exports
are unchanged. The investigation stayed within Increment 3; Increment 4 remains
deferred. The user subsequently authorized committing the verified milestone.
